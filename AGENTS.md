# ScipionAPI — developer manual for AI agents

Read this before making changes here. Written for an AI coding agent, not end users — see `README.rst` for that.

For deeper, less-frequently-needed context, see:
- [`.ai/tech-debt.md`](.ai/tech-debt.md) — known problem areas, with file:line
- [`.ai/roadmap.md`](.ai/roadmap.md) — planned/likely future work (draft, pending team review)
- [`.ai/postgresql-runtime-compatibility.md`](.ai/postgresql-runtime-compatibility.md) — mandatory PostgreSQL runtime Set, streaming, concurrency, and legacy SQLite compatibility rules

## What this repo is

A FastAPI backend exposing Scipion project management, protocol interaction, output browsing/previews, plugin inspection, and auth over a REST API. Part of the intended replacement for the Tkinter desktop GUI (alongside ScipionWeb, the React frontend that talks to this backend). **Not standalone** — runs inside a Scipion-capable Python environment and imports `pyworkflow`/`pwem` directly at runtime (`app/backend/runtime/*`, `app/backend/utils/outputs_preview.py`), and depends on `scipion-app`'s `PluginRepository` (`app/backend/api/services/plugin_service.py:15`).

## Stack

FastAPI + Uvicorn, PostgreSQL via SQLAlchemy 2.0 + Alembic migrations, Celery + Valkey for task brokering/result storage, JWT auth(`app/backend/utils/jwt.py`). **`pydantic` is pinned to 1.10.x** (`requirements.txt:22-23`, conditional on `python_version`) — this is deliberate, not an oversight; introducing Pydantic v2 syntax (`model_config`, `field_validator`, ...) anywhere will break the build until a real migration is planned.

## Architecture map

- `app/backend/api/` — FastAPI routers.
- `app/backend/mapper/` — data-access layer (SQLAlchemy models + a separate flat Postgres mapper for some relational features, e.g. project shares). SQL lives here, not in `api/services`: a mapper class takes `db` and has one method per query, with the SQL as module constants so integration tests can run them (e.g. `streaming_monitor_mapper.py` for the streaming monitors, `protocol_activity_mapper.py` for the bell).
- `app/backend/models/` — Pydantic (v1) request/response schemas.
- `app/backend/project/`, `app/backend/runtime/` — the layer that actually talks to Scipion (`pyworkflow`/`pwem` imports live here).
- `app/backend/utils/`, `app/backend/viewers/` — including `outputs_preview.py`, which imports `pwem.emlib`/`pwem.viewers` directly.
- `app/workers/` — Celery worker + config (`celery_worker.py`, `celeryconfig.py`).
- `scipionapi_cli/` — a separate, packaged admin/provisioning CLI (`scipionapi` console script): `bootstrap.py`, `provision.py`, `db.py`, `admin.py`, `doctor.py`. This is what sets up Postgres/Valkey/the Scipion env for a fresh install — not "clone and pytest," there's a real provisioning flow. `update.py` (`scipionapi update`) checks before changing anything that each disk it writes to (scipion_home, the Python environment) has `SCIPIONAPI_UPDATE_MIN_FREE_GB` free (default 5; a full `/` stopped PostgreSQL and a pip build on a server), keeps its temporary files (pip builds, the Web archive check) under `scipion_home/updates/work/<stamp>/tmp` instead of `/tmp`, and removes its work directories when it ends (a failed one stays until the next update, without its temporary files).
- `tests/{unit,integration,smoke}/` — `integration/` needs real Postgres+Valkey running (`tests/integration/db/test_migrations.py`, `tests/integration/workers/test_task_queue.py` will fail without them); `unit/` and `smoke/` don't.

## Packaging

`pyproject.toml` is the authoritative dependency definition for both the
ScipionAPI backend and the packaged `scipionapi_cli` CLI.

Runtime dependencies live in `[project].dependencies`. Test-only
dependencies (`pytest`, `pytest-asyncio`, `httpx`) live in `[project.optional-dependencies].test`.

## Testing

- CI already exists: `.github/workflows/tests.yml`, matrix Python 3.8–3.12 (3.8 and 3.9 on ubuntu-24.04: setup-python has no builds of them for later Ubuntu), `pytest.ini` with `testpaths = tests`, using `actions/checkout@v7` and `actions/setup-python@v7`.

- `pytest-asyncio` is part of the test extra; keep it compatible with Python 3.8–3.12 so marked async tests execute throughout the CI matrix.
- The thumbnail route tests call their coroutines with `asyncio.run()` from ordinary tests, so those checks also execute when async plugin loading is disabled.

- `tests/smoke/` (e.g. `test_app_import.py`, `test_main_app.py`) is the fastest thing to run to sanity-check the app still imports/boots.

## PostgreSQL runtime Set contract

PostgreSQL is the only authoritative runtime persistence for Scipion Sets. Temporary SQLite files are allowed only as worker-local compatibility snapshots for legacy code that explicitly calls `Set.getFileName()`.

These snapshots must remain under `/tmp/postgresql-runtime-sets/worker-<PID>/`, must be isolated per consumer worker, and must refresh at the same path when the PostgreSQL revision changes. Never replace this with one SQLite file shared by the producer and consumers, and never create compatibility SQLite files inside `Runs/`.

Input restoration and compatibility materialization must not mutate or persist parent protocols or their canonical outputs.

Ordinary-item compatibility snapshots initialize their SQLite schema from the
complete persisted PostgreSQL columns before copying items, so optional fields
first present in later items remain readable. Do not infer that schema only
from the first item or scan all items to build it.

Runtime Set iteration uses independent server cursors with `WITH HOLD`, decodes
rows in batches and hydrates only consumed objects. At commit, PostgreSQL spools
remaining source rows on the server while preserving their snapshot. Hydrators
prepare access-path metadata per schema and still resolve owners and call native
setters for every row; custom hydration hooks retain the generic path.
Pointer-free items with primitive values can consume their own freshly
collected graph during serialization. Never reuse item values between appends;
custom conversion/introspection hooks keep the general serialization route.
The graph of each item class is read along the shape learnt from its first item
(`ScipionSetPostgresqlMapper._getItemGraph`): the attribute names, order and
classes of every object and their storage/pointer flags are checked on each
item while its values are read, and any difference sends that item through the
general walk. A shape is kept only if its walk gave exactly the general walk's
result on the item it was learnt from (`test_postgresql_item_graph_plan.py`).
Native runtime appends use a compact buffer that keeps rows as JSON text in
memory and spills them above 8 MiB, in pickled blocks, into an anonymous
worker-local temporary file until the existing flush boundary; a failed spill
leaves the buffer as it was. Custom serializers retain deferred conversion. Root bulk writes update canonical and logical item tables in
one SQL statement per chunk, inside one transaction covering the entire flush.
Preserve rollback/retry behavior and both stored representations.

Nested runtime Sets revalidate their current logical table with a scoped
identity query instead of loading every class or tilt-series table. Native
child appends are buffered without a lookup per item; flushing revalidates
the table and restores queued schema paths if it was replaced. Schema growth
still validates the current table before writing columns. Once an
owned writable child mapper has flushed, parent updates may reuse its exact
persisted table without copying the child items again. External/SQLite-backed
children and mismatched or pending mapper scopes still use snapshot import.
Set properties read a Set's sampling-rate getter before falling back to its
first item, avoiding implicit SQLite materialization of native class Sets.
Child reads resolve the table identity once per query, never per hydrated
row. A parent's `_setItemMapperPath` hook does not export the parent for
runtime children, which load their own mapper; subclass hook code still runs.
Set iteration builds a new item per row by default. `SCIPIONAPI_SET_ITEM_TEMPLATE=1`
opts into native template reuse for `iterItems()`/`for x in set` (honoring
`SCIPION_MAPPER_USE_TEMPLATE`); `set[id]`, `getFirstItem()` and `iterate=False`
always return independent objects, and nested Set items are always built anew.
Enable it only once every plugin in use clones the items it keeps; code here
that keeps iterated items must clone them or pass `iterate=False`.
Runtime `append()` does not go through a Set's `_insertItem`, so it calls the
Set's `_validateNewItem(item)` when defined (e.g. tomo Sets refusing a repeated
tsId) before storing: keep native admission checks working there. Where filters
accept `field IN (v1, ...)` lists, which streaming consumers load batches with.

Neither canonical root nor logical items keep a JSON GIN. Migration
`b75a4e291c0f` drops the canonical root GIN; `9d064ee31b1b` dropped the
partial nested GIN (added by `41c8d93e7a62`). Normal reads use the scoped
item indexes. Rare or absent undeclared-field type lookups scan a root Set,
which can cost more for very large Sets. Dynamic logical-field discovery still
reads both parent populations in one statement so legacy null-parent rows
remain readable. These migrations run concurrently, retry failed builds, and
do not change item data. Migration `6b00be24a501` indexes the child-table
lookup on `scipion_set_tables ("setId", "parentItemId")` and drops item
indexes that repeat the primary key or the leading column of the unique
`(setId|tableId, scipionItemId)` constraints; do not re-add them.
Runtime Sets expose `appendFromStoredSets()` (pwem's join and id subsets use it) to copy
whole stored Sets with one `INSERT … SELECT`. It only runs when the copy is
provably identical to appending the built items one by one, and otherwise
writes nothing and returns False; keep that guarantee when extending it.

Read [`.ai/postgresql-runtime-compatibility.md`](.ai/postgresql-runtime-compatibility.md) before changing runtime Sets, streaming inputs, `getFileName()`, `Set.load()`, output restoration, or SQLite materialization.

## Metadata viewer tables

- A table sorted by a column other than the id (`postgresql_dao._getSortedRowsPage`) is sorted once in PostgreSQL, ids only, and kept per process (`_SORTED_ORDER_CACHE`, keyed by table, column, direction and the Set's and its logical table's last write, `_sortVersion`); each window then reads only its rows by id. Sorting again at every window scrolled to cost the whole Set each time.
- `renderMetadataImageCellsBatchService` shares one `batchContext` among its cells: the table is opened once, the rows asked for by index are read in one window (`_batchRowValues`, when they are closer than `_METADATA_BATCH_ROW_SPAN`) and one `OutputsPreview` renders the MRC images. Each cell opened the table, read a page of rows for one and built its own renderer.
- `_metadataLock` still serialises the table requests (tables, schema, pages, windows, row position, export) of every user. Each request builds its own ObjectManager, and image cells already run without it, but it may cover module-level registrations of `metadataviewer`; it was left in place until that is shown safe.

## CTF viewer (SetOfCTF)

- `GET .../outputs/{o}/ctf` (`viewers/postgresql_ctf_reader.py`) lists every CTF of the Set, as the viewer draws its plots and statistics from all of them. It reads only the values a row shows (`listStoredSetItemsWithKeys` with `LISTED_VALUE_PATTERN`, keys matched by their end as `_buildCtfRow` does), keeps the list per process by Set version (`updatedAt`, `itemsCount`), and the route answers gzip compressed when the client takes it (`_compressedJson`, for routes listing thousands of rows only: images are compressed already).
- `.../ctf/{id}/psd` and `.../ctf/{id}/micrograph` read one item (`getStoredSetItem`) and the Set without its items (`limit=0`): never the whole Set at every row clicked. Their renders are kept per process (`_CTF_IMAGE_CACHE`, by file version and parameters) with an ETag and `Cache-Control`, and an `If-None-Match` that matches answers 304.

## Protocol viewers on the web

ScipionWeb builds each plugin's desktop "Analyze results" viewer (`ProtocolViewer`) at runtime instead of porting viewers by hand:

- `protocol_viewer_dynamic_form_worker` loads the project, restores the protocol's inputs and attaches its stored outputs, instantiates the viewer and serializes its form (`POST .../viewers/runtime-preview`). The reply lists the fields with a visualize handler as `actions`.
- `protocol_viewer_action_worker` runs one handler of `_getVisualizeDict()` with every `View.show()` (and `pyplot.show`) captured and translates each View into a descriptor: message, plot (PNG), table, text, image, data (a stored output reference, or a project file) or unsupported (`POST .../viewers/action`).
- Project files shown by an action travel as signed tokens (`protocol_viewer_file_token_service`) used in place of the output name in the output metadata routes, so the existing MetadataViewer reads `.sqlite`/`.star`/`.xmd` files and their blocks.
- Both run in short-lived child processes; they protect the API from crashes and timeouts but are not a sandbox: plugin viewer code runs with the server's privileges, as protocols do. Enabled by default for any authenticated user with access to the project (`protocol_viewer_settings_service`); a server can switch them off with `SCIPION_EXPERIMENTAL_PROTOCOL_VIEWER_HTTP=0` (no viewers on the web) or `SCIPION_EXPERIMENTAL_PROTOCOL_VIEWER_EVAL=0` (no viewer code is run). Timeouts: `SCIPION_PROTOCOL_VIEWER_FORM_TIMEOUT` (default 60 s) and `SCIPION_PROTOCOL_VIEWER_ACTION_TIMEOUT` (default 120 s).
- Viewer workers are forked from a warm process (`protocol_viewer_warm_worker`, handled by `protocol_viewer_warm_pool`) that has already imported Scipion and the plugins: an action takes ~0.3 s instead of ~1.7 s. Each request still gets a fresh child process (killed with its group on timeout). The warm process restarts when the plugins or environment revision changes or a loaded module file changes (plugins edited in develop mode), and is warmed up when the web lists a protocol's viewers. If it cannot run a request, a one-shot worker does. Switch off with `SCIPION_PROTOCOL_VIEWER_WARM_WORKER=0` (unit tests do so by default).
- Viewer handlers may write cache files in the protocol folder, as on the desktop (e.g. CL2D's `classes_scipion_level_XX.sqlite`). A handler that fails half-way can leave an empty one that later runs reuse.

## Actions of a running protocol

- The desktop context menu of a running protocol shows `protocol.getActions()`: STOP STREAMING of a streaming import (`ProtImportImages`: movies, micrographs, particles) and APPROVE CHECKPOINT of pwem's checkpoints. Each callback only leaves a file in the run folder (`extra/STOP_STREAMING.TXT`, `extra/APPROVE_CHECKPOINT.TXT`) that the running protocol looks for: the import then closes its output Set and finishes on its own, and the streaming protocols after it finish in turn. Marking it finished (or aborting it) instead would leave its Set open, and the protocols after it waiting for ever. The tomography tilt series import has none.
- `GET /projects/{p}/protocols/{id}/run-actions` (labels) and `POST` the same with `{action}` (`api/services/protocol_run_actions_service.py`). The user needs access to the project, and only a protocol whose status is `running` starts a child: the others offer nothing. The child (`protocol_run_actions_worker.py`, through the viewers' `_run_worker` and warm pool: add any new worker module to `ALLOWED_MODULES` of `protocol_viewer_warm_worker.py`, or it always starts cold) loads the protocol with `loadRuntimeProtocol` (the project folder as working directory, so the callback writes where the protocol looks) and runs again `getActions()` before running the one asked for. Callbacks get the menu event (`stopImport(self, e)`) or nothing (`stopWait(self)`). Plugin code never runs in the API process.

## Protocol summary (the desktop Summary tab)

- `GET /projects/{p}/protocols/{id}/summary` (`api/services/protocol_summary_service.py`) answers `{lines, objects, hasWarnings}`. After the project access check, a child (`protocol_summary_worker`, through the viewer workers' `_run_worker`) loads the protocol with its inputs and stored outputs, runs `checkSummaryWarnings()` and `summary()` (the plugin's `_summary()` plus the comment, the error and the warnings) and names the protocol output of every object of its inputs and outputs by id, for the `[[sci-open:ID][name]]` links. The lines keep Scipion's markup; a line may hold several (`\n`). Errors answer the run actions' codes. Methods are not served (not wanted on the web).
- Loading the project is most of a summary's cost (the summary itself takes milliseconds), so `protocol_summary_service` keeps each answer (in memory, per API process, at most 512, for an hour at most) with a fingerprint of what the summary reads: `ProtocolSummaryMapper` (`mapper/protocol_summary_mapper.py`) folds into one text the protocol's status and `updatedAt`, its top-level `scipion_objects` (with their values), the `scipion_sets` of the protocol and of its parents (`protocol_input_refs`; `parentIds` is not reliable), with their `properties` (closing a stream changes them without moving `updatedAt`), and its input refs. An unchanged fingerprint answers the kept summary with that query (~10 ms instead of ~2-3 s); two readers of one protocol start one child. A write that changes what a summary shows must move one of those columns.

## Protocol form wizards on the web

A form param's wizard is the one the desktop form opens (`Domain.findWizards(protocol, 'tkinter')`, attached by `protocol_wizard_service.findWizardsWeb`). The web runs the wizard's own `show(form)` in a worker (`protocol_wizard_runtime_worker`, forked from the warm viewer worker; `POST /projects/{p}/wizards/run`), never in the API process. The worker builds the protocol as the form shows it (stored protocol with its inputs restored, plus the form values) and hands the wizard a `HeadlessForm` (`protocol_wizard_runtime`): `setVar` calls become the web form's `paramUpdates`, message dialogs become messages, and every other dialog is replaced at class level (dialogs block inside their constructor, and plugins import the classes by name). The first dialog reached stops the run and is described to the web (`confirm`, `choice`, `form`, `list`, `preview`, `file`, `point_in_volume`); the web runs the wizard again with the answers so far, each dialog takes its answer, and the plugin code converts the values itself. Preview dialogs (mask radius/radii, downsample, CTF, band-pass, gaussian) use the desktop's initial values and ranges, and their images come from the same Xmipp calls (`readPreview`, `fastEstimateEnhancedPSD`, `bandPassFilter`, `gaussianFilter`); a `preview` request returns images for an item and values. Display Views a wizard shows (plots) come back as viewer items. A dialog class with no web counterpart replies `unsupported`. Same switches and timeouts family as the viewers (`SCIPION_EXPERIMENTAL_PROTOCOL_VIEWER_EVAL=0` disables it; `SCIPION_PROTOCOL_WIZARD_TIMEOUT`, default 180 s). Viewer forms have wizards too (e.g. the color scale of local resolution viewers, targeting viewer classes): the viewer form lists them (`wizards`, field -> wizard id, found with `Domain.findWizards(viewer, 'tkinter')`), and `POST /projects/{p}/protocols/{id}/viewers/wizard` runs one in `protocol_viewer_wizard_worker` with the viewer as the form's protocol and the viewer form values applied; replies are the same as `/wizards/run`. Params put on one line (`addLine`, e.g. that color scale) are serialized as fields of their group.

## Xmipp particle picking on the web

`XmippProtParticlePicking`'s interactive step opens Xmipp's Java picker. The web offers the same session (`xmipp_picking_router`, `xmipp_picking_session_service`): it reads and writes the picker's own files in the protocol's `extra/` folder (`<micrograph>.pos` with `header`/`particles`/`particles_auto` blocks, and `config.xmd`) in exactly the Java format (`xmipp_picking_files`), so a session can move between the web and the desktop picker. Micrographs come from the protocol's stored `inputMicrographs` input; "create coordinates" reads the session with Xmipp's `readSetOfCoordinates`, as the desktop's coordinates button does. As on the desktop, Launch opens the picker: while a protocol runs, `launchSupervisedPickerGUI` is replaced (`web_interactive_picker.webInteractivePickers`, around `protocol.run()` in the protocol worker) by a web session whose `wait()` blocks like the Java process. The step and the web talk through files in `<extra>/.scipionweb_picker` (a refreshed `session.json`, `register-<id>.json` requests answered by the step running `registerCoords`, and `close`). The project page polls `GET /projects/{p}/picking/open-sessions` while protocols run and opens the picker; closing it ends the step, which leaves the protocol interactive. Switch off with `SCIPION_WEB_INTERACTIVE_PICKER=0` (the Java window then opens as before). Supervised training (Xmipp's `AutoParticlePicking2`) is only reachable through JNI, and its `correct` needs the candidates of the previous autopick in memory, so each picking folder keeps one classifier process (`xmipp_classifier_session`, running `app/backend/runtime/XmippPickerSession.java` headless with Scipion's Java setup; closed after 15 idle minutes). Like the Java picker on the desktop, it lives with the protocol's waiting step: the API reaches it through `classifier-<id>.json` requests in the step's channel (`StepClassifier`), and it ends when the picker closes. Only a picker opened on a protocol that is not waiting (e.g. finished) keeps it in the API process. Train/Next (`/picking/micrographs/{micId}/train|next`) follow the Java picker: training uses every micrograph with manual particles (the trained one last) and rejects candidates inside the trained area; Next only corrects with the candidates of that micrograph's autopick: `correct` pairs the corrections with them by position, and they live only in the classifier's memory, so a new classifier process (idle close, API restart) autopicks a still-Supervised micrograph again (same model, same candidates) and corrects only if the candidates match the stored ones. The trained area is kept in `extra/.web_classifier_trained.json` for the same reason. Templates and centering follow `SupervisedParticlePicker` and run in the same Java process with Xmipp's JNI calls (`alignImage`/`applyAlignment`/`getRadialAvg`/`bestShift`): particles are boxed from the micrograph as the picker shows it, with `config.xmd`'s ImageJ filters applied (the usual ones through their ImageJ classes, as `IJ.run` needs a display for some; a new `config.xmd` stores the Java defaults, Gaussian blur σ=2 and enhance contrast). `POST .../picking/micrographs/{micId}/pick` centers a new particle on the templates' radial average once there are more manual particles than templates (shifts of a quarter of the box or more are ignored), and in manual mode adds it to the templates; `.../moved` adds a moved manual particle. A new size or number of templates rebuilds them from the manual particles (manual mode, at most 50, or 10 when bigger than 256 px). `templates.stk` is written only when every template is filled, as in Java; Xmipp's automatic picking protocol requires it next to the `model_*` files, so training (and closing a trained session) writes it from the manual particles when missing, with a plain average only if the bindings fail. Writes to a session folder are serialized by a thread lock plus a file lock (`extra/.web_picker.lock`), so several API processes can serve the same session. The step's heartbeat runs in its own thread, so a long training does not make the session look closed.

## Volume surface meshes

`GET .../volumes/{id}/surface` runs marching cubes on the (reduced) volume (`utils/volume_surface_mesh.py`). With `format=binary` it returns `encodeSurfaceMeshBinary`: `SMSH`, the header length (uint32 LE), a JSON header (every field except the arrays, plus `arrays`: name, type and length) padded to 4 bytes, and the arrays `vertices`/`normals` (float32), `indices` (uint32) and `values` (float32). The web asks for it (`parseVolumeSurfaceMeshBinary`); JSON stays the default. The two formats are cached apart. The normals are the marching cubes ones (or those of the smoothed surface, oriented the same way: pointing out of the density), and the web uses them as they are. Every level of a volume shares one frame (`frame: "box"`): vertices are `(voxel - center) / scale` with `center = shape/2 - 0.5` and `scale` the largest side of the reduced volume, so it does not depend on the reduction. The web computes surfaces in the same frame in the browser (`surface-nets.ts`, for the live threshold and the inner level), and they line up with the API ones. Bump `_VOLUME_SURFACE_MESH_VERSION` (part of the cache key and ETag) when the mesh output changes.

## Tilt series viewer images

The web tilt series viewer draws the tilts itself from `GET .../tiltseries/{id}/stack?indices=&maxDim=` (`renderTiltSeriesStackService`, `utils/tilt_series_stack.py`): each tilt is reduced by block averaging from its float values, its mean and standard deviation are measured without outliers, and it is sent as 8 bits over mean +/- 5 std (`low`/`high` in the header), with its `rot`/`shiftX`/`shiftY`. The web loads it in chunks from the current tilt outwards, applies the contrast (a window in standard deviations, per tilt or for the whole series) and the alignment on a canvas, exactly as the previews place it (scipy rotation counterclockwise on screen, then the shift, then the vertical flip; checked against `ImageStack.transformSlice`). Frames are resolved like `renderTiltSeriesImageService` (`_tiltSeriesFrameSources`), so both show the same image. The PNG previews (`/tilt`, `/tilt/batch`) stay for an API without the stack.

## Tomogram slices in the coordinates viewer

`GET .../coords3d/tomograms/{id}/volume?maxVoxels=` (`renderCoords3dTomogramVolumeService`, `utils/volume_stack.py`) sends the tomogram reduced by block averaging to at most `maxVoxels` (default 64 M), as 8 bits over mean +/- 5 robust std, in one `TVOL` binary (z, y, x). MRC files are memory mapped and reduced a few planes at a time; the last few results are kept in memory. The web cuts every slice of every axis from it (`tomogram-slices.ts`, as `readVolumeSlice2d` cuts them: z rows y, y and x rows z) with one contrast window for the whole tomogram, and shows them as paletted BMP object URLs, so the SVG images and 3D plane textures work as before. The `/slice` route still serves the slices until the volume arrives.

## Protocol output thumbnails (project cards, graph nodes)

`GET /projects/{id}/thumbnails?scope=card|graph&size=` lists the thumbnails and `GET .../outputs/{name}/thumbnail-image?size=&sig=` serves one (`app/backend/thumbnails/`). Neither loads the project nor takes `_thumbnailProjectLock`:
- `catalog.py` reads the outputs from the database (`loadPersistedOutputSummariesByProtocolId` + `protocols`), scores them with `scoreOutputClass` (shared with `ThumbnailService._scoreOutput`) and signs each one with its class, `updatedAt`, `itemsCount` and `maxItemId` (+ `RENDER_VERSION`; bump it when thumbnails are drawn differently). A growing (streaming) output gets a new signature, hence a new thumbnail.
- `store.py`: `<project>/.thumbnail_cache/v3/p<protocolId>/<output>_<size>_<sig>.webp` (+ `.missing` when it cannot be drawn); sizes snap to `SIZES`; writing one drops the older signatures. Checking a thumbnail is a file stat.
- `scheduler.py` draws the missing ones in a process pool (`SCIPION_THUMBNAIL_WORKERS`, default 2-4), jobs of `JOB_SIZE` outputs of one project (one project load each, `_runRenderThumbnailsJob` in `runtime/preview_process_executor.py`, `ThumbnailService.renderProtocolOutputThumbnailBytes`), never queuing an output twice. The image route waits up to 4 s, then answers 202; images whose URL names the current signature are `immutable`.
The images are read as their original values and reduced before the contrast is set (`_read2dTile`, `_readImagePreview`, `_displayImage`; movies average a few frames). In the metadata viewer a movie cell (a table of a SetOfMovies or SetOfTiltSeriesM, `_isMetadataMovieOutput`) is drawn by `outputs_preview.movieDisplayImage`: the first frame of a TIFF read with Pillow (it decodes LZW; pwem's reader needs imagecodecs and reads one frame anyway), or every frame of a TIFF of at most 10 (a tilt of a tilt series movie: a few e/A^2 over a few frames), decoded in threads; two frames of an MRC read from a memory map; else pwem's stack; each reduced with Pillow, with the contrast set at 512 px and only then shrunk to the cell (set on a 128 px cell it closed on the noise left and burnt it to black and white, or a frame of 8-bit counts rounded to black). The tilt series viewer does the same for a SetOfTiltSeriesM (`isMovieSet` of the tilt series reader): each tilt is a movie file of its own, drawn from the mean of its frames (`movieMeanImage`), never as frame <tilt index> of it, and the tilts of a series stack are read `TILT_MOVIE_READ_THREADS` at once. `METADATA_IMAGE_DISPLAY_VERSION` is in the cell cache key: bump it when cells are drawn differently. The old routes (`/thumbnail`, `/thumbnail-items`, `/output-thumbnails`) and their v2 cache remain for clients without the new ones.

## Deleting projects, protocols and workflows

Large deletions must not keep the request waiting:
- Folders are removed with `utils/background_delete.deleteInBackground`: renamed into a `.scipion-trash` folder (instant; the project root for protocol folders, the projects folder for projects) and removed by a background thread. Protocol delete, reset and restart (`RuntimeProtocolResetService._cleanWorkingDirInBackground`, instead of `protocol.cleanWorkingDir`) use it.
- Set items have no foreign key (migration `b7d2e9f41c08`): deleting a `scipion_sets` or `scipion_set_tables` row, directly or through a cascade from a protocol or project, makes a statement trigger queue its id in `scipion_set_item_purges`, and `utils/set_item_purge` removes the queued `scipion_set_items`/`scipion_set_table_items` in batches of 20000 (one thread per server process, started in `main.lifespan`; an advisory lock lets only one process purge; it polls every 60 s and `requestSetItemPurge()` wakes it). Never delete items of a whole Set by hand when the Set itself goes: that is the slow part the queue avoids. Set and table ids are never reused, so any read filtered by `setId`/`tableId` or joined to its Set never sees queued items. Measured with `tests/benchmarks/db/test_workflow_operations_benchmark.py` (40 protocols x 20000 particles: Reset from 10.9 s -> 0.6 s, Restart 3.4 s -> 0.4 s, Delete 2.3 s -> 0.2 s).
- A project is first marked `status = 'deleting'` (and renamed `name#deleting-id`), which hides it from `getProject`/`listProjects`; its rows are deleted afterwards in the background with their own connection (`scheduleProjectRowsDeletion`). At start-up (`main.resumeBackgroundDeletes`) the pending project deletions are resumed and the projects trash is purged.
- The cascading deletes find children by `protocolDbId`/`objectId`; migration `7a1c2e9d4f30` indexes those columns (without them each deleted protocol scanned whole tables).
- `POST .../protocols/delete` and `.../reset-from` accept `includeWorkflow=false` to skip rebuilding the project afterwards (the web reloads it itself).

## Users, roles and permissions

- **Permissions** are the fixed catalogue of `app/backend/api/permissions.py` (`plugins.manage`, `settings.manage`, `jobs.manage`, `users.manage`, `roles.manage`, `groups.manage`, `projects.create`, `projects.share`, `projects.viewAll`, `projects.manageAll`, `files.browseServer`, `files.download`, `facility.*`…). Routes ask for one with `Depends(requirePermission("..."))`, services with `checkPermission(user, "...")`; nothing checks `users.role` any more (kept only as a label).
- **Roles** (`access_roles`, `access_role_permissions`, migration `c3f8a1d6e2b4`) are sets of permissions an administrator creates. `Administrator` is the system role: it holds every permission, cannot be changed or deleted, and at least one active user always keeps it. The install's admin gets it (`scipionapi_cli/admin.py`). New accounts get the `isDefault` roles (User) and stay inactive until an administrator activates them.
- **Groups** (`user_groups`, `user_group_members` with `member`/`pi`, `user_group_roles`): a user holds the permissions of their own roles and of their groups' roles (`AccessPostgresqlMapper.getUserPermissions`). `getCurrentUser` returns them in `permissions` (and `isSystemAdmin`); `/auth/me` too.
- **No one gives what they do not hold** (`AccessService`): giving roles or groups to users, editing roles and changing a group's roles or members are refused if they grant a permission the actor lacks; only a holder of the system role gives it.
- **Projects**: `PROJECT_ACCESS_SQL` (in `mapper/postgresql.py`) gives each project's `access` for a user as the most of owner (manage), shares with the user or their groups (`project_shares.permission`: `view`/`work`/`manage`, with `userId` or `groupId`) and roles (`projects.manageAll` or the system role: manage; `projects.viewAll`: view). `getProject`/`listProjects` use it. Every route of the project, 2D-coordinates and picking routers checks it before running (`project_access.projectRouteAccess`, a router dependency bound to the router's own `getMapper`): GET routes need view, the others work, and `MANAGE_ROUTES` (rename, delete, share) manage; `VIEW_ROUTES` lists the POST routes that only read. `PERMISSION_ROUTES` adds global permissions (create/import, share, download link). A new project route needs no change unless it only reads through POST or manages the project; `tests/unit/backend/api/test_route_authentication.py` fails when a route is unchecked or a table names a route that does not exist.
- The signed download (`fs/download-file`) has no user, so it lives in `project_router.publicRouter`.
- **PIs** (migration `e6c1b9a4d203`): each group has `piAccess` (`none`/`view`/`work`/`manage`, `view` to start with), what its PIs may do in the projects its members own; `PROJECT_ACCESS_SQL` adds it as one more source and says where the access comes from in `accessVia` (`owner`, `share`, `group`, `role`). Raising it needs as much over every project (`view`: `projects.viewAll`; `work`/`manage`: `projects.manageAll`), lowering it does not.
- **Audit log** (`audit_events`, same migration; `app/backend/api/audit.py`, `mapper/audit_mapper.py`): routes call `recordAudit(mapper, actor, "category.action", targetType, targetId, targetName, details)` once what they did succeeded (a refused sign-in too). It takes the route's mapper (or a db) and never fails the request; without a database it keeps nothing. Async routes with no mapper (plugins) use the `@audited(action, targetType, describe)` decorator, and `recordAuditOwnConnection` opens a connection for one event. `ClientAddressMiddleware` keeps the client's address for the events. Recorded: `auth.*` (sign-in, refused sign-in, sign-up, password), `users.updated`, `roles.*`, `groups.*`, `projects.*` (create, import, rename, delete, share, unshare), `settings.*` (the names of what changed, never environment values), `plugins.*`, `jobs.worker`. Protocol runs are not audited. `GET /access/audit` (`audit.view`; `action` is an action or a category, `text`, `since`, `until`, paged with `before`/`nextBefore`) and `GET /access/audit/categories` (`AUDIT_CATEGORIES`) read it. Events are kept for ever for now; the actor's email stays when the account is deleted.
- Users have `createdAt` (migration `d4a7c2e8f915`). Holders of `users.manage` get the inactive accounts created since the bell's `since` in `GET /workspace/protocol-activity` as `status: "account"` events (`workspace_service._pendingAccounts`, `AccessPostgresqlMapper.listPendingAccountsSince`).

## Facility mode (branch `lims`, in progress)

A facility layer on top of ScipionWeb, off by default: `SCIPIONWEB_FACILITY_MODE` (Settings → Environment, `settings_service.SCIPIONWEB_VARIABLES`; `1` turns it on, read per request). Off, ScipionWeb is what it always was: every `/facility/*` route but `GET /facility/status` answers 404 (`facility_service.requireFacilityMode`) and the web shows no facility menu. Projects never depend on it; a session (to come) only points to the projects it makes.
- `GET /facility/status` → `{enabled, permissions}`: the `facility.*` permissions the user holds, empty when off (the web's menu).
- Microscopes (`routers/facility_router.py`, `services/facility_service.py`, `mapper/facility_microscope_mapper.py`, migration `a3d9e5f1c260`): `facility_microscopes` (model, status operational/maintenance/out_of_service, energy filter, acquisition software, voltage, Cs, the folder it writes to, whether it runs sessions) and its detectors (migration `f4c8e1a7b392`): `facility_detectors` (name unique in the microscope, the name the acquisition metadata gives it — EPU's BM-Falcon, EF-CCD... — whether it is behind the energy filter, gain path with flip/rotation, notes) and `facility_detector_pixel_sizes` (calibrated pixel per magnification, per detector: the same magnification is another pixel on each camera). The microscope is saved with its detectors in one transaction, like the sample tree: a detector keeps its id (a session will record which one took its movies), one without an id is new, the ones left out are deleted with their calibration, ids of another microscope are refused; the name unique is DEFERRABLE so two detectors may swap names. The migration made one detector per name of the old comma-separated text (or "Camera" when there was none but a gain or a calibration), the first taking the microscope's gain and table; its downgrade puts them back. Any `facility.*` permission lists them; `facility.manage` creates, edits and deletes them (audited as `facility.microscope*`, category `facility`). A microscope may have a photo (`facility_microscope_photos`, migration `c7e2a4b9d815`): `PUT /facility/microscopes/{id}/photo` takes a PNG, JPEG or WebP body (up to 15 MB), kept as a WebP of at most 1600 px turned as the camera held it (`facility_service.photoForWeb`), in the database so it goes with its backups; `GET` serves it to the staff (the list's `photoUpdatedAt` versions its address), `DELETE` removes it; both changes are audited.
- Samples and grids (`services/facility_sample_service.py`, `mapper/facility_sample_mapper.py`, migration `d5b1f8c3e742`): `facility_samples` (NZ code, unique whatever its case; description, group, owner, access route), `facility_grid_boxes` (label unique in the sample, vitrification code and date) and `facility_grids` (position 1–12 unique in the box, grid number, type, concentration, specimen, status stored/loaded/used/discarded). `GET/POST /facility/samples`, `PUT/DELETE /facility/samples/{id}` (`?q=` searches code and description): any `facility.*` permission lists them, `facility.sessions` or `facility.manage` saves them, audited as `facility.sample*`. A sample is saved with its whole tree in one transaction: rows with an id are updated (a grid keeps its id for good: a session's DATA will point to it), rows without one inserted, the sample's boxes and grids left out deleted; ids of another sample are refused. The label and position uniques are DEFERRABLE (checked at commit), so a save may swap two grids. Samples, boxes and grids keep images (`facility_images`, migration `e3a6c9d2f458`: each image belongs to exactly one of them, `num_nonnulls` check, and goes with it): `POST /facility/{samples|boxes|grids}/{id}/images?caption=` takes a PNG, JPEG or WebP body kept as a WebP of at most 2048 px (`facility_service.photoForWeb`), up to 20 per owner, by whoever saves samples; `GET /facility/images/{id}` serves it to any facility staff, cached for good (an image never changes); `DELETE /facility/images/{id}` removes it. The sample tree lists each level's `images` (id, caption, date; never their bytes). Images are kept at once, not with the tree's save. The image SQL is shared (`mapper/facility_image_mapper.py`; the sample and session mappers extend it), and `insertImage` commits in its own transaction. A grid a session took data from stays: a save that leaves it out, or deleting its sample, answers 409.
- Sessions (`services/facility_session_service.py`, `mapper/facility_session_mapper.py`, migration `a8d2c5f7e913`): `facility_sessions` (name unique, microscope RESTRICT, technique spa/tomo, status planned/acquiring/finished/archived, group, user, EMhub booking ref, day, startedAt/finishedAt set when the status first leaves planned / reaches finished, staff notes, createdBy) and `facility_session_datasets` (kind atlas with number 0, or data with number 1–12, unique in the session and DEFERRABLE; grid RESTRICT; detector SET NULL; notes). Each answered dataset carries its `folder`: `<name>_ATLAS` or `<name>_DATA_NN`, what the operator types into EPU. The name follows the facility's convention, `YYYY_MM_DD_<Name-Surname>_<6-digit id>` (`sessionName`: the day, the user's name in plain ASCII or the group's, the id taken with `nextSessionId` before the insert), unless one is given (letters, digits, `_ - .`); it can change only while planned. A save keeps the ATLAS (one always) and the datasets' ids (the watcher will put the detector and the project on them), deletes the ones left out, refuses ids of another session and detectors of another microscope; only a microscope with `sessionsEnabled` takes a new session, a microscope with sessions cannot be deleted (409), and only a planned session can be deleted. `GET /facility/sessions?status=active|all|<status>&q=` (active: planned and acquiring) and `GET /facility/sessions/{id}` for any facility staff; `POST/PUT/DELETE` for `facility.sessions` or `facility.manage`, audited as `facility.session*`. Sessions and datasets keep images (`POST /facility/{sessions|datasets}/{id}/images`; `facility_images` gained `sessionId`/`datasetId`); `DELETE /facility/images/{id}` answers the session when the image was a session's.
- `facility_service.detectorFor(detectors, cameraName)`: the detector that took a movie whose metadata names cameraName — its metadata name, then its name, regardless of case; a microscope with a single detector has it; else None.
- `facility_service.calibratedPixelSize(detector["pixelSizes"], magnification, nominalPixelSize)`: the calibrated pixel of an acquisition, by magnification, else the one nearest the nominal pixel within `PIXEL_SIZE_TOLERANCE` (0.02 A; EPU writes other decimals), else None to keep the nominal one.
- Plan and facility decisions: the LIMS stage 1 plan (sessions → one project per DATA tied to its sample NZ and grid, Talos pilot, everything on Galileo, tomography after SPA).

## Remote file browser (`fs/*` routes)

The web's file browser (`RemoteFileDialog`) reads `GET /projects/{p}/protocols/{id}/fs/start-path|list|preview|preview2|download` and writes with `POST .../fs/write`. Where it may look is decided in one place, `api/services/fs_browser.py`:

- `scope=project` (default): the project folder; browsing starts in the protocol folder (`<project>/Runs/%06d_<class>`, taken from the database, so no request loads the project; a protocol never run starts in the project folder). Symbolic links under it may lead elsewhere, as Scipion links its inputs.
- `scope=filesystem`: the whole filesystem, read only, starting in the protocol folder. Without `files.browseServer`, and when `SCIPIONWEB_DATA_ROOTS` (folders separated by `:`; install and update write `/`, which limits nothing; listed and editable in Settings → Environment through `settings_service.SCIPIONWEB_VARIABLES`, a web edit overriding the `.env`) is set, only the project folder and those data folders are reached; listings of the folders above them show only the way to them, and `start-path` returns them in `allowedRoots` (and the data folders alone in `dataRoots`, for the browser's shortcuts; `/` is left out). Downloads (not inline previews) need `files.download`. The same reach is checked when protocols are launched, restarted or continued (`fs_browser.checkLaunchPaths`): every path parameter in use (`PathParam`, `FileParam`, `FolderParam`) and an import's `filesPath` + `filesPattern` up to its first wildcard, relative paths read from the project; a path out of reach answers 422 with the reason. Launches without a user, and data folders that include `/`, are not checked. Protocol forms use it for their path parameters, because imports read data from other disks; the picked path is kept relative to the project when it is inside it and absolute otherwise.
- import (project and protocol ids `-1`): projects and workflows to import, under `SCIPION_IMPORT_BROWSER_ROOT`, never above `SCIPION_IMPORT_BROWSER_CEILING` (`/home`); a project elsewhere has to be copied under it first.

Writes go inside the project, or, in the import area, only as `.json` files outside hidden folders (exported workflows); never with `scope=filesystem`. The start-path answer includes `projectRootAbs` so the browser can offer the project folder. Listings come from `os.scandir` with `mtime` and `isLink`; text previews show at most 1 MB (the end of a log, the start of anything else, marked `X-Preview-Truncated`); `.star`, `.xmd`, `.csv` and `.tsv` preview as tables (`utils/star_table.py`: every `data_` block, its first 200 rows and how many there are, reading the file line by line).

**Uploads from the user's computer** (`routers/project_upload_router.py`, `services/project_upload_service.py`): a file goes into the project's `Uploads/` folder, in chunks, so a big file passes a proxy's request limit and a dropped connection resumes. `POST /projects/{p}/uploads` {name, size} opens it (a plain visible name, never a path; the size limit `SCIPIONWEB_UPLOAD_MAX_GB`, default 10, 0 = none, in Settings → Environment; free disk space for it plus 2 GB, or 507); `PUT .../uploads/{id}?offset=N` appends the raw body (at most 64 MB; an offset other than what arrived answers 409 with `received`, which `GET .../uploads/{id}` also gives); `POST .../uploads/{id}/complete` names it with a hard link, so an existing file is never replaced (409), and records `projects.fileUploaded` in the audit log; `DELETE` drops it. Partial files and their descriptions live in `Uploads/.partial`, belong to the user who started them, and are removed after a day of no change when another upload starts. The router's guard needs work access and `files.upload` (granted with `files.download` by migration `f2b8d4c6a917`). The web offers it in the protocol form's file browser (Upload button and dropping a file on the list) and selects the file once it is there.

Downloads: a plain link cannot carry the bearer token, so `POST .../fs/download-link` (authenticated, checked against the same boundary) returns a signed link (`fs_download_token`, HMAC with `SECRET_KEY`, bound to the absolute file, user and project, valid 2 hours) to `GET .../fs/download-file?token=`, which needs no bearer token. The browser's own download manager then streams the file to disk, shows progress and resumes it with range requests (Starlette `FileResponse`) when the connection drops, e.g. over a VPN. `fs/download` also streams now instead of reading whole files into memory. Signed links are only as safe as `SECRET_KEY`: it must be set in production (it also signs the JWTs).

## Workspace, overview, streaming monitor, disk usage and launch history

- `/workspace` router (`api/services/workspace_service.py`), cross-project, so it is not under `/projects/{projectId}` (an int route there would swallow it):
  - `GET /workspace/protocol-activity?since=`: runs that ended in any of the user's projects. Clients pass the server `now` of their previous answer, the lookback is capped to 6 h, and the end time is the last step's `endTime`.
  - While something runs, the projects with a live protocol (at most 10) also report monitor alerts, of micrographs and of tilt series (`tomo_monitor.alertsSince`: runs of consecutive tilt series past a threshold, cached 10 s too) (`status: "alert"`, `threshold`, `endedAt` = when the run started): runs of consecutive micrographs past a threshold among the newest 300 points of their followed stream (`streaming_monitor.alertsSince`) that started after `since`. A run whose first point is the oldest one looked at is left out (it may have started earlier). The runs of a project are cached 10 s per process, so every open tab polling the bell costs one computation. A monitor that fails is logged and skipped.
- `GET /projects/{p}/overview` (`project_overview.projectOverview`): runs by status; running, failed, recent and longest runs. Run times come from the protocol steps (first `initTime` to last `endTime`).
- `GET /projects/{p}/monitor` (`api/services/streaming_monitor.py`, queries in `mapper/streaming_monitor_mapper.py`): the live monitor of a single particle stream.
  - Acquisitions (`api/services/stream_branches.py`, both monitors): each import is one (movies or micrographs, tilt series or their movies, whose protocol reads none of the outputs the monitor follows; a CTF consensus writes micrographs but reads CTFs). The monitor follows the branch of one of them (`?acquisitionSetId=`, else the open one that received something last, then the one with more items): the import and every protocol made from it through the input refs, plus the outputs made from no acquisition (imported particles, unknown inputs). What comes after two branches are joined belongs to both. `_chain` and the selectors (`ctfOutputs`, `coordinatesOutputs`, `classesOutputs`, `tiltSeriesOutputs`), the flow and the dose see only that branch; the exposure window looks upstream over the whole project, so a union of two imports stays ambiguous. The answer lists `acquisitions` (with `stage`, `items`, `streaming`, `lastItemAt`) and `acquisitionSetId`. The bell looks at every open acquisition (at most `MAX_ALERT_BRANCHES`, 5), else at the followed one, and tells a run shared by two branches once.
  - The chain follows the CTF output (the newest one, or `?ctfSetId=`): the micrographs it read and the movies they came from, upstream through `protocol_input_refs`, and downstream the coordinates and particles made from those micrographs. The picker may read the chain's micrographs or those of any protocol in between that writes micrographs or CTFs again (a CTF consensus, a shift filter…): `_pickings` lists every picking of the project with its extraction (through any coordinates filter or picking consensus) and the 2D classes made from it (through any particle filter or preprocessing), and how far it is from the followed CTF (`_downstream`; None from another branch). The followed one is `?coordinatesSetId=`, else the one leading to `?classesSetId=` (the 2D classes asked for, listed in `classesOutputs`), else the one that goes furthest (to 2D classes, then to particles), then one from the followed stream, then the nearest, then the newest; `coordinatesOutputs` lists them. 2D classes no picking leads to are shown anyway (the newest). A protocol with no input ref to a parent the graph says it depends on (`protocol_dependencies`) reads every output of that parent. Backlogs are counted on what each protocol reads: the micrographs the picker reads (`pickedFrom`), the particles the classifier reads (`classifiedFrom`). Tomography outputs are not followed.
  - `?qualityWindowSize=N` (1–5000) adds an `exposures` snapshot of the last `2*N` imported movies in database row/import order. It follows the selected chain upstream through movie filters to its unambiguous source and joins matching movie/micrograph/CTF item identities only within that chain. The snapshot refreshes late CTF and picking independently of incremental cursors; missing processing stays explicit. Movie merges without an unambiguous identity return null, as do micrograph-only imports. SQL reads are bounded and scoped by Set. Omit the parameter (or 0) for the original response without the snapshot.
  - Stage counts come from the Set counters in `scipion_sets.properties` (`itemsCount`, `maxItemId`, `streamState`), so nothing is counted. Rates count the items created in the last 10 min and the 10 before (a trend arrow), among the newest 5000 of each Set only (`RATE_SAMPLE`, read through the `(setId, scipionItemId)` index), so a poll costs the same after a million particles; a Set filling the sample faster than that gets the sample's own rate and no trend.
  - Without a CTF output the micrographs of the aligner give the points (drift only, `series.kind = "micrographs"`): the micrographs of a protocol reading movies that no micrograph-writing protocol made (a max shift filter reads aligned movies; a categorization or a tilt analysis, with its discarded micrographs, reads micrographs). Without micrographs the imported movies are followed (an output whose protocol reads no movies), so a stream shows from its first movies. Once a CTF output appears the series moves to it and starts again.
  - "The newest" output (`_newest`, and the last tie-break of the followed picking) is the one made last, by Set id, never the one written last: in streaming two protocols running side by side (two CTF estimations, two pickers) take turns at being written last, and the monitor would jump between them at every poll.
  - Dose: the analysis followed is one whose movies carry `_MEAN_DOSE_PER_ANGSTROM2` that the movies it reads do not; the protocols after it (motioncor) copy the dose onto their own movies and are not followed.
  - The CTF series is incremental: the client passes `afterSetId`/`afterRowId` (the `lastRowId` of its previous answer) and gets at most 2000 new points (`more` says there are more). The cursor is the item row id, the order rows were written in, not the item id: parallel steps finish items out of order, and one with a lower id written later must still be read. Another `setId`, or a Set whose rows were all written again (its first row id is above the cursor), answers `reset: true` and starts again.
  - A point's time is when its item was written (`creation`, else `createdAt`), that is, processing time: Scipion keeps no acquisition time.
  - Drift: the frame-to-frame path of the `_alignment` shifts of the movies the aligning protocol writes (not the ones it read, which have none) times its pixel size (total and largest step, as Xmipp's max shift filter). The movie, its micrograph and its CTF share the item id. Without usable shifts it falls back to the micrograph's `_rlnAccumMotionTotal`, which motioncor and Relion keep when they dose weight.
  - `alignedMicrographs`: the micrographs the aligner wrote, as a stage of their own (rate, backlog) when the micrographs the CTF reads come from a later protocol (a categorization, a preprocessing); otherwise they are the `micrographs` stage.
  - Coordinates and particles per micrograph: each process keeps a count per micrograph of the followed coordinates and particles Sets (`countByMicrograph`, keyed by `_micId` or `_coordinate._micId`) and adds the rows written since the last poll through the row id, at most 50000 per poll (`MIC_COUNT_CHUNK`), so a restart counts again over a few polls (`counting: true`) instead of grouping millions of rows at once; a Set whose first row is above the ones counted is counted again. Their stages report `micrographs` and a backlog in micrographs (with a CTF and not picked yet, a micrograph with nothing picked counting as waiting; picked and not extracted yet), only once counted. `picking` sends the coordinates of the micrographs whose count changed since the client's `afterPickSetId`/`afterPickRowId`.
  - 2D classes (a SetOfClasses2D reading the followed particles, e.g. Xmipp's alignPCA-2D in streaming): a `classes2d` stage (classes, `particles` classified, and as backlog the extracted particles not classified yet; no rate, its rows are classes) and `classes` (each class with its particles from its child table's `itemsCount`, biggest first, and `version` = the Set's `updatedAt`). The protocol rewrites its averages in the same file every round, so the monitor asks for their images (the metadata image route, `contrastMode=enhanced`) with `version`, which is part of the image cache key and ETag.
  - Stages with a backlog carry `etaMinutes` (backlog / rate of the last 10 min; coordinates and particles turn their rate into micrographs with their items per micrograph) or `stalled` when nothing moved (`withEta`, used by both monitors).
  - Each point lists the thresholds it goes past (`alerts`). The defaults are the facilities monitors' (defocus 1000–40000 Å, astigmatism 1000 Å) and Xmipp's max shift (10 Å per frame, 45 Å in total); the CTF resolution and `minParticles` (fewer coordinates picked on a micrograph) have none. `PUT /projects/{p}/monitor/thresholds` keeps a project's own in `project_monitor_settings` (migration `9c4e2a7b1d63`); a null threshold raises no alert. A database without the table uses the defaults.
  - `flow` (`api/services/stream_flow.py`): whether the stream flows. The acquisition is the import the stream's movies come from (an output whose protocol reads no movies, up through any protocol writing movies again), else its micrographs. The import closes its Set itself once its `timeout` passes with no new files, or when told to stop, so a closed import is a `finished` acquisition, never a pause. An open one is `paused` after `maxMoviePauseMinutes` (10) with no new item, with `importClosesInMinutes` from the protocol's `timeout` (read with `durationSeconds`, never pyworkflow's `strToDuration`, which evaluates the text), or `stopped` when its protocol does not run. A stage whose Set is still open, with items waiting and no new item for `maxStageStallMinutes` (15), is stalled (`stalledMinutes`); a closed Set never is (what it lacks was left out), nor are 2D classes (made in rounds). `complete`: finished, every stage closed. The last item of each Set comes from the rate query (`newest`). The bell gets these as runs too, starting when each condition began (the last item plus the threshold; the end of an acquisition, when its Set closed), so they are told once.
  - The tomography monitor has a `flow` too (`tomo_monitor._flow`, thresholds `maxTiltPauseMinutes` 10 and `maxTiltSeriesStallMinutes` 30). Its acquisition is the import of the movies of the tilts, else the acquired tilt series. A tilt series is made with its first tilt and gets the others one by one, so the acquisition last gave something with its newest tilt (the latest `time`/`updatedAt`/`tiltsUpdatedAt` of its rows), not its newest tilt series; and the tilt series still being acquired waits for no stage (`readyBehind`: the backlog of the stages reading the acquired ones, minus the incomplete ones).
- `GET /projects/{p}/monitor/tomo` (`api/services/tomo_monitor.py`): the tomography stream, one row per tilt series.
  - The chain starts from the acquired tilt series (an output whose protocol reads no tilt series, nor anything made from them: IMOD's fiducial alignment reads the fiducial model, not tilt series, see `MADE_FROM_TILT_SERIES`; `?tsSetId=` to choose) and follows, through any protocol writing tilt series again, the CTF series, the aligned tilt series (those the reconstruction reads, else ones holding an aligned tilt series), the fiducial models and the tomograms. Tilt series movies (SetOfTiltSeriesM) are not followed.
  - A tilt series is complete once its child table holds `_size` tilt images. Per tilt series, its tilt images (enabled ones, angle range, highest dose) and its CTF series (failed tilts with the -999 defocus or disabled, mean defocus and astigmatism, worst resolution) are summarised once per change of their rows (`updatedAt`, tilt counter) and kept per process, so a poll reads root rows only.
  - The fiducial residual is read from the landmark model's text file (`_fileName`: x y tiltIm chainId xResid yResid, px), once per file version; AreTomo stores none.
  - Thresholds (shared table and route with the single particle monitor): `minTilts` 30 and `minAngleSpan` ±50° (judged once complete), `maxFailedCtfTilts` and `maxResidual` with no default, and the CTF ones of the single particle monitor.
  - `GET .../monitor/tomo/tiltseries?tsId=`: its tilts by acquisition order with their CTF, the shifts and rotation of the aligned tilt series and the residual per tilt. `GET .../monitor/tomo/tomograms/{setId}/{itemId}/slice?size=`: the central slice, through the volume slice cache (keyed by the file's mtime).
- `GET /projects/{p}/disk-usage`: walks `Runs/<id>_<class>` without following symbolic links. The count runs in a background thread and is cached in memory for 15 min, per process. While it runs, the answer has `computing: true`. `?refresh=true` counts again.
- `protocol_launches` table (migration `4e8b1d2c7a55`): `ProjectService.launchProtocol` stores the protocol's persisted `params` after every successful launch, restart, continue or schedule (keys starting with `_` are dropped), with the user and the mode. Recording never fails a launch: a database that is not migrated only loses the history. Read it with `GET /projects/{p}/protocols/{id}/launches`.

## Protocol tags

Tags belong to a project. Every collaborator of a shared project may edit them. Titles are unique per project, in any case (`ux_protocol_tags_project_lower_title`). Tag ids are global, and the client may choose them.

- Create: `insertProtocolTag` never overwrites. An id in use (in any project) or a title in use raises `ProtocolTagConflict`, which becomes a 409 with a clean message.
- Update: changes only the fields sent; null clears description and color.
- Validation: `tags_schema.py` checks title ≤ 80, hex colours and tag id format.
- `PUT .../protocols/{id}/tags` (`setProtocolTagIdsByProtocolDbId`):
  - runs in one transaction, with the protocol row locked;
  - keeps only tags of the project and returns what the protocol has now (`tagIds`), plus `ignoredTagIds`.
  - The graph query only reports tags of the protocol's project.
- Copies:
  - duplicating a protocol copies its tags (`copyProtocolTagAssignments`);
  - exported workflows carry each protocol's tags by title under the `scipionWebTags` key, which Scipion ignores;
  - import or paste reuses the target project's tag with that title, or creates it (`ensureProtocolTag`).
- The SQLAlchemy model `tag_model.py` matches the migrated schema, and a test checks this. Keep it in sync so `alembic --autogenerate` never proposes dropping `projectId`.

## Known gotchas

- **`pyproject.toml` currently pulls `scipion-pyworkflow`, `scipion-em`,and `scipion-app` from Yunior's fork `devel` branches rather than the official Scipion repositories. This is intentional while the fork remains ahead of upstream.
- **Runtime-generated persistence artifacts are not source files**: files such as `dump.rdb` and `.backend_reload_marker` are gitignored and must remain untracked.
- **Valkey intentionally still uses the Redis Celery transport/client stack**: `celery[redis]`, `redis-py`, and `redis://`/`rediss://` URLs remain correct. Do not replace them merely because the server is Valkey.
- `pydantic==1.10.x` pin (see Stack above) — a real, easy-to-violate-by-accident constraint.
- **Plugins installed in develop mode while the backend runs** (`pip install -e`) are importable only through the `.pth` file the install writes, which the interpreter reads only at startup. The Domain refresh (`scipion_domain_refresh_service`, on every plugins revision bump) processes the `.pth` files written or changed since the process started (`PathFileTracker`) before registering new plugins. Keep that order, or workflows imported after such an install silently lose the new plugin's protocols.
- **Attributes a protocol creates while running** (scalars that are not form params, e.g. cryoSPARC's `projectName`/`workSpaceName`/`currenJob`, or `summaryVar`) are stored with the protocol params under `_scipionRuntimeAttributes` and restored when the protocol is rebuilt (`app/backend/runtime/protocol_runtime_attributes.py`). Classic Scipion stores them too, and Continue, summaries and viewers read them. Attributes the server manages itself (status, timing, job/pid, host) are excluded, and so are outputs (created ones and `_possibleOutputs`): a scalar output restored as a plain attribute stops plugins that create it only when missing (crYOLO's `if not hasattr(self, "boxsize")`). Duplicating a protocol does not copy them.
- **A streaming child starts once its input Set has been written with items, not when the first row appears** (`RuntimePostgresqlProtocolWorker.getReadinessState`, `publishedItemsCount` from the Set's stored `_size` in `ProtocolGraphRepository.getPostgresqlRuntimeOutputInfo`). An appended item is stored at once, but the Set's own attributes (`_hasOddEven`, `_hasAlignment`...) reach the database only at `Set.write()`. Warp appends an empty tilt series, then its tilts, then `update()` + `write()`: a child that started on the first row read `hasOddEven() == False`, and IMOD's protocols, which decide odd/even once at start, dropped the odd/even files of every output. Classic children only see the output after `_store`, so this matches it.
- Protocol viewers that launch a desktop program (`CommandView`, e.g. ChimeraX): the program opens on the server's own screen when the API process has a display (`DISPLAY`/`WAYLAND_DISPLAY`, i.e. ScipionAPI and the browser on the same computer) and the program is installed; switch off with `SCIPION_PROTOCOL_VIEWER_DESKTOP=0`. The volumes it would open (files or `open` lines of its `.cxc`/`.py` script) are also offered to the web volume viewer through a multi-file viewer token (`ViewerFileVolumeReader`).
- Protocol viewers that open a page with `webbrowser.open*` (e.g. a cryoSPARC job) produce a `link` result that the web opens in the user's browser.
- `scipion_home/` is gitignored and holds a local `.env` — not a leak, just local config; don't assume secrets belong there or that it's meant to be committed.
